Alata ships a cache layer with a pluggable store behind a single facade — file, Redis, database, memory, or null, wired up by the framework's providers at boot. Your application code just imports `Cache` and calls it, in async or sync contexts alike. A fresh scaffold defaults to the zero-dependency file store; switch to Redis (or the database store) for multi-worker deployments.

```python
from alata.cache import Cache

await Cache.aput("greeting", "hello", ttl=300)
value = await Cache.aget("greeting")   # "hello"
await Cache.aforget("greeting")
```

## Configuration

Cache configuration lives in `config/cache.py`:

```python title="config/cache.py"
from config.settings import settings

CACHE_CONFIG = {
    # Default store. Override via CACHE_STORE env var.
    "default": settings.CACHE_STORE,
    # Global key prefix — prevents collisions when multiple apps share a backend.
    "prefix": settings.CACHE_PREFIX,
    # Named stores available through Cache.store(name).
    "stores": {
        "redis": {"driver": "redis", "connection": "cache"},
        # "table" names the cache table (locks live in "{table}_locks"),
        # "connection" picks a named database connection. Requires the
        # shipped create_cache_table migration to have run.
        "database": {"driver": "database", "table": "alata_cache", "connection": "default"},
        "file": {"driver": "file", "path": None},
        "memory": {"driver": "memory"},
        "null": {"driver": "null"},
    },
}
```

| Key | Default | Purpose |
| --- | --- | --- |
| `default` | `file` | Name of the store to use by default (`CACHE_STORE` env). |
| `prefix` | `alata_cache:` | Prepended to every key. Lets multiple apps share one backend safely. |
| `stores` | — | Named store definitions; each picks a `driver` (`redis`, `database`, `file`, `memory`, `null`) plus driver options. |
| `strict_locking` | `True` | Whether lock acquisition fails when Redis is down (see [Locks](#atomic-locks)). |
| `async_client_binding` | — | Optional container binding name whose async Redis client the cache should reuse. |

### The database driver

The `database` driver keeps the cache in a relational table — shared across
every worker and server that talks to the same database, with no Redis
required. Options: `table` (default `"alata_cache"`) names the entry table,
`connection` a named database connection, `prefix` overrides the global key
prefix. Locks live in a companion `{table}_locks` table so flushing the
cache can never release a held lock.

The scaffold ships a `create_cache_table` migration that creates both
tables (`alata_cache`: key, value, expiration; `alata_cache_locks`: key, owner,
expiration) — `alata migrate` picks it up like any other migration. If you
configure a custom `table` name, rename the tables in that migration to
match. On MySQL the migration also pins the `key` column to the
`utf8mb4_bin` collation, so keys compare byte-for-byte the way they do on
PostgreSQL; MySQL's default collation is case- *and* accent-insensitive,
which would let `User:ABC`, `user:abc` and `user:abç` share a single row.

Writes upsert with the database's native conflict clause, and `increment`
is a single atomic upsert statement, so counters — including the
[rate limiter's](/docs/digging-deeper/rate-limiting) fixed windows — are
correct under concurrency across processes. Expired rows are treated as
misses and deleted on read.

<Callout type="warn">
Keys are limited to **255 characters**, including the global prefix — the
width of the `key` column. A longer key raises `ValueError` naming the limit
rather than being silently dropped. Hash the user-supplied part of long keys,
or widen the column in your migration and raise
`DatabaseCacheStore.KEY_MAX_LENGTH` to match.
</Callout>

At boot, `CacheProvider` builds the configured store and binds it in the [service container](/docs/architecture/container) as `cache`. The Redis store is handed *resolvers* for two container bindings: the sync client `redis.cache` and the async client `redis.cache.async` — both registered by the Redis provider from your `config/redis.py` (see [Named Redis connections](#named-redis-connections)). It also resolves a dedicated `redis.lock` connection so lock traffic never competes with cache traffic; if you haven't configured one, locks share the cache connection.

<Callout type="info">
The cache degrades gracefully. If Redis is unreachable — at boot or mid-flight — reads return `None` and writes are silent no-ops. The degradation is deliberate but never silent: the first failure is logged at **WARNING** (once per store), the rest at debug. Clients are re-resolved on every operation, so the cache starts working again on its own once Redis recovers — no restart, and no process stuck with rate limiting permanently off. The provider falls back to a no-op store only when *no* Redis connection is registered at all, which is a configuration fact rather than an outage.
</Callout>

<Callout type="warn">
While degraded, counters do not accumulate — so anything counting attempts
(the [rate limiter](/docs/digging-deeper/rate-limiting) most of all) sees zero
and lets every request through. Treat the WARNING as an alerting signal.
</Callout>

## The Cache API

`Cache` stores **string values**. Methods follow the framework-wide naming rule: the plain name (`get`, `put`, ...) is synchronous, and the `a`-prefixed twin (`aget`, `aput`, ...) is the one to `await`. The examples below run in async contexts — handlers, queue tasks — so they use the `a`-prefixed forms.

### Retrieving and storing

```python
# Read — returns None on a miss, or your default
value = await Cache.aget("stats:daily")
value = await Cache.aget("stats:daily", default="0")

# Write — ttl is in seconds; None means no expiry
await Cache.aput("stats:daily", "42", ttl=3600)
await Cache.aput("config:banner", "on")          # no expiry

# Existence and removal
if await Cache.ahas("stats:daily"):
    ...
await Cache.aforget("stats:daily")
```

<Callout type="warn">
A non-positive `ttl` is not "expire immediately" — the write is silently skipped. Pass `ttl=None` for a key that should live forever.
</Callout>

### Cache-aside with `aremember`

`aremember` returns the cached value if present, otherwise runs your callback, stores the result, and returns it. The callback may be sync or async. It is async-only — there is no sync counterpart:

```python
async def fetch_dashboard(user_id: str) -> dict:
    return await Cache.aremember(
        f"dashboard:{user_id}",
        ttl=300,
        callback=lambda: build_dashboard(user_id),  # sync or async
    )
```

By default `aremember` serializes with `json.dumps` and deserializes with `json.loads`, so dicts and lists round-trip transparently: you get the structured object back on both cache hits and misses. Pass your own `serializer`/`deserializer` pair for other types. A callback returning `None` is not cached.

### Counters

`increment` adds to a counter key atomically and returns the new count. A
missing (or expired) key is created at `amount` and stamped with `ttl`
seconds; an existing key keeps its original expiry, so increments never
extend the window — which is what makes fixed-window counting correct.

```python
attempts = await store.aincrement("login:u1", 1, ttl=60)
```

Every driver agrees on the two edge cases:

| Case | Behavior |
| --- | --- |
| `ttl` of zero or less | The counter is created with **no expiry**. (`put` treats a non-positive `ttl` differently — it skips the write entirely — because a counter that expires the moment it is created can never accumulate, silently disabling rate limiting.) |
| The existing value is not an integer | The stored value is **left untouched** and `0` is returned. It is never destroyed and never replaced by a counter. |

<Callout type="info">
The `redis` and `database` drivers increment with a single atomic
statement. The `file` driver cannot, so it serializes its read-modify-write
behind a short-lived guard file scoped to the key. Only the writer that took
a guard releases it, and a guard is taken over only once its expiry has
genuinely passed — a crashed holder. A writer that waits out
`FileCacheStore._GUARD_TIMEOUT_SECONDS` (5s) raises `CacheGuardTimeoutError`
rather than stealing a live guard and dropping counts. For counters under
heavy multi-process contention, prefer `redis` or `database`.
</Callout>

### Bulk removal

```python
# Delete every key under a prefix (the global prefix is applied on top)
deleted = await Cache.aforget_by_prefix("dashboard:user123:")

# Clear the whole store
await Cache.aflush()
```

Prefixes are matched **literally**. Characters that would be wildcards in the
backend's own pattern language — `*`, `?`, `[`, `]`, `\` for Redis, `%` and
`_` for SQL — are escaped, so `forget_by_prefix("q[abc]:")` deletes exactly
the keys starting with `q[abc]:` and nothing else.

When a global key prefix is configured, `flush` deletes only your app's prefixed keys — it will not wipe another application's data on a shared Redis, and two file stores pointed at one directory with different prefixes never clear each other. Locks are out of reach entirely: on every driver they live in a namespace of their own (see [Atomic locks](#atomic-locks)), so neither `flush` nor `forget_by_prefix` can release a lock somebody is holding — clearing the cache is not a lock reset.

### Atomic locks

`Cache.alock` acquires a distributed lock atomically (SET NX EX) and returns an **owner token**, or `None` if the lock is already held. Pass the token back to `aunlock` so you only ever release your own lock — the release is an atomic compare-and-delete, immune to the race where your TTL expires and another process acquires the lock between check and delete:

```python
token = await Cache.alock("reports:rebuild", ttl=60)
if token is None:
    return  # someone else is doing it

try:
    await rebuild_reports()
finally:
    await Cache.aunlock("reports:rebuild", owner=token)
```

Sync contexts use the plain `Cache.lock` / `Cache.unlock` pair — same semantics, same token protocol.

Locks are namespaced apart from values on **every** driver — a `lock:` sub-namespace under the global prefix on Redis, a table of their own on the memory store, separate `locks/` files on the file store, and the companion `{table}_locks` table on the database store. A lock and a cache value under the same logical key are different entries that never interact: writing or forgetting the value cannot release the lock, holding the lock never shadows the value, and `flush`/`forget_by_prefix` operate on values only.

The `strict_locking` config key decides what happens when Redis is unavailable: with `True` (the default) `lock` returns `None` — acquisition fails, so uncoordinated concurrent execution is impossible; with `False` it returns a synthetic token and lets the operation proceed, which suits idempotent work like scheduling mutexes.

### Sync usage

For code that runs outside an event loop — [console commands](/docs/digging-deeper/console), migrations, scripts — call the plain names, backed by the sync Redis client. Drop the `a` prefix and the `await`:

```python
value = Cache.get("key")
Cache.put("key", "value", ttl=300)
Cache.forget("key")
Cache.has("key")
Cache.forget_by_prefix("dashboard:")
```

[Async and Sync](/docs/basics/async-and-sync) covers which variant belongs in which context.

### Named stores

`Cache.store(name)` resolves an alternative store registered in the container under `cache.<name>`. The framework registers `cache.null` (a no-op store) out of the box; bind your own in a provider to add more. Requesting an unregistered name raises `CacheStoreNotConfiguredError`, whose message lists the stores that *are* available.

```python
store = Cache.store("null")
await store.aput("ignored", "value")
```

### Testing

Swap the facade's store without touching the container:

```python
Cache.fake()        # NullCacheStore — all reads miss, writes vanish
Cache.fake_dict()   # DictCacheStore — in-memory with real TTLs, for asserting values
Cache.restore()     # back to the real store
```

```python
def test_caches_dashboard():
    fake = Cache.fake_dict()
    try:
        ...
        assert fake.get("dashboard:u1") is not None
    finally:
        Cache.restore()
```

## Key prefixing

The Redis store prepends `CACHE_CONFIG["prefix"]` (default `alata_cache:`) to every key. Your code always works with logical keys — `Cache.get("stats:daily")` reads `alata_cache:stats:daily` from Redis. The prefix applies to `forget_by_prefix` too, and scopes `flush` to your own keys.

## Named Redis connections

The cache rides on the framework's Redis provider, which is useful in its own right. `config/redis.py` declares named connections:

```python title="config/redis.py"
from config.settings import settings

CONNECTIONS = {
    "default": {"url": settings.REDIS_URL},
    "cache":   {"url": settings.REDIS_CACHE_URL or settings.REDIS_URL},
    "queue":   {"url": settings.REDIS_QUEUE_URL or settings.REDIS_URL},
}
```

For each entry, `RedisProvider` registers two lazy container singletons:

- `redis.<name>` — a sync client (`decode_responses=True`), pinged at first resolution; resolves to `None` if Redis is unreachable. The ping is bounded (3s connect, 5s operation), so a host that drops packets rather than refusing them fails fast instead of stalling startup.
- `redis.<name>.async` — an async client that connects lazily on first command.

```python
from alata.container import container

redis = container.make("redis.default.async")
await redis.sadd("online", user_id)
```

Connections that share a URL are **deduplicated**: when `REDIS_CACHE_URL` is unset and falls back to `REDIS_URL`, `redis.cache` is an alias for the same physical client as `redis.default` — no wasted connections. On application shutdown the provider closes every client that was actually resolved.

Add your own entries — for example a dedicated `"lock"` connection, which the cache provider picks up automatically for lock traffic — and they become `redis.lock` / `redis.lock.async` with no further wiring.
